## Order and dependencies

**A → B → C → D → E.** Each plan leaves `main` green and shippable on its own.

- **A before B:** a swap re-runs `explain`. With names stored as references (A), the warnings of
  an edited roster follow later renames like every other roster's.
- **B before C:** the yearly balance is read from what was actually worked, which after B
  includes hand edits. C stores the balance on the roster in both places a roster is made
  (`makeRoster` and the swap), so writing it after B touches each place once.
- **C before D:** independent in code; C changes the solver and D changes the schema, and doing
  the model change first keeps the golden snapshot's diff about one thing.
- **D before E:** both redraw the month grid. E's polish lands on D's three absence types instead
  of being redone.
- **Later, the sick-call recalculation** reuses B's `editRoster` pipeline (solve or edit →
  `validateRoster` → `explain` → balance), the undo bar and the changed-cell marks.

## Shared decisions

- **One schema bump in all of v2: D takes `schemaVersion` from 1 to 2.** A, B and C add only
  optional fields (`Roster.edited`, `Roster.balance`) that v1 data simply lacks, so no migration.
- **The input fingerprint stays as it is.** Names, the yearly history and hand edits don't make
  a roster outdated: names only change the display, the history is only a tie-breaker, and an
  edit is the roster itself.
- **Archived weeks stay read-only:** no swaps in them, and their stored balance counts towards
  the year like any other week's.
- **Every roster change goes through one checked path:** `validateRoster` → `explain` → balance.
  A roster that breaks a strict rule is never saved, whether the solver or a swap made it.

## A. Warning texts follow renames

**Problem.** `explain` writes names into the warning texts at solve time. After a rename, the
table shows the new name and that roster's warnings keep the old one — on screen, in print and in
the Excel footnotes.

**Design.** `explain` writes a **name reference** instead of the name: the staff id between two
private-use characters, `<id>`. Nobody types those, and they never reach the screen:
`resolveNames(text, staff)` swaps each reference for the person's current display name (`?` for an
id no longer on the list). It runs wherever warning text is shown: the warnings panel, the print
footnotes and the Excel footnotes. `core/names.ts` holds both functions, so `core/` stays pure.

- Rosters saved before A hold plain names. They show as they are, so nothing needs migrating.
- The day cards keep stripping the leading day name (`Hétfő, 1. cs.: …`); a reference never
  sits at the start of a text, so the prefix check still works.
- Deleted and inactive people stay on `state.staff` (hidden), so old rosters keep resolving.

**Rejected:** re-running `explain` at display time. It needs the exact input the roster was
solved from, which is gone once anything changes, and archived weeks would lose their warnings.

## B. Hand editing: swap two people

**What she does.** In the roster table she clicks a name, then another name **on the same day**.
The two swap everything about that day: shift, seat, opener or closer. If the swap keeps every
strict rule, the roster updates at once, the undo bar says *"Csere: Anna ↔ Bea, szerda."* and the
two cells are outlined. If it doesn't, nothing changes and a line says why: *"Ez a csere nem
lehetséges: dajka nem ülhet óvónői helyre."*

- **A selection bar** while one name is picked: *"Anna kiválasztva (szerda) — kattints arra, akivel
  cserél. [Mégse]"*. Clicking the same name again, *Mégse*, or Escape cancels. Clicking a name on
  another day moves the selection there.
- **Only in an open, current roster:** not in archived weeks, not while it's outdated (she
  re-solves first), not while solving.
- **Re-solving drops hand edits,** so Számol asks first when the roster has any: *"A kézi cserék
  elvesznek. Újraszámolod?"* The roster carries `edited: true` for that, and the week bar shows a
  small *kézzel módosítva* note.

**Engine.** `core/edit.ts`:

- `swapDay(roster, staff, date, a, b)` exchanges the two assignments' `shift`, `seat`, `opener` and
  `closer`, then recomputes `substitution` from the role (a teacher in a nanny seat). Pure.
- `editRoster(input, roster, change)` runs the swap, then `validateRoster`; on a violation it
  returns `{ ok: false, violations }`, otherwise the roster with fresh warnings and
  `edited: true` — the same result type as `makeRoster`.

A **violation → Hungarian reason** table in `hu.ts` covers the rules a swap can break
(`nannyInTeacherSeat`, `keyNotNanny`, `openerEveryDay`, `closerEveryDay`), with a generic fallback.

**Decision: same-day swaps only.** Each day stands alone in the roster; swapping Anna's Monday with
Bea's Tuesday means nothing when both work both days. Moving someone into an empty seat (a hole)
is not a swap and stays out: the solver already fills every hole it can, so a remaining hole needs
someone called in, which the call-in button does.

## C. Yearly balance

**Her rule** (spec §2): *as equal as possible — within the period first, across the kindergarten
year second.* When a period can't be split evenly, the extra unit goes to whoever has had less of
it this year.

**What counts.** The same four counts as the period fairness (§6.3): morning shifts, opener days,
closer days, reserve days. For each saved roster, the **delta** of each person's count from their
fair share in that period, `count − num / den`, taken from `fairShares`. A person's yearly balance
of a kind is the sum of their deltas over the kindergarten year's rosters **before** the week being
solved. The kindergarten year runs **Sep 1 – Aug 31**, so the balance resets on Sep 1.

**Stored, not recomputed.** A past week's fair shares depend on its exact input (who was active,
the absences, the group counts), which later edits change. So each roster stores its own deltas
when it is made — `Roster.balance`, written by `makeRoster` and by `editRoster` — and the year's
balance is their sum. Rosters saved before C have none and count as zero. **Decision:** acceptable,
since v1 went live on 2026-09-27 and has no real history yet.

**In the solver: a seventh stage, `yearly`, after turnarounds** (spec §6.5 names it as the last
tie-breaker). Its objective is `Σ balance[p][kind] × count[p][kind]` over every share: someone ahead
on a count is steered away from more of it, someone behind towards it. Stages 3–4 have already
fixed every gap at its optimum, so this only decides who gets the rounded-up unit. Its objective is
fractional; as the last stage it needs no bound afterwards. The history reaches the solver as
`SolveInput.history`, built by `solveInputFor` from the saved rosters, and stays out of the input
fingerprint.

**Where she sees it.**

- `UNEVEN` names the reason: *"Egyenlő elosztás nem volt lehetséges: Nóra 3 délutános műszak az
  5-ből. Idén eddig 2 délutánnal kevesebb jutott neki."* The added sentence appears only when the
  yearly balance of that count is at least 1 whole day either way.
- **Éves egyenleg** — a folded table at the bottom of the Munkatársak tab: per person the year's
  morning / afternoon, opener, closer and reserve counts, each with its difference from a fair share
  (`+2`, `−1`). It answers "why me again?" with numbers.

## D. Richer absences

**Types.** Each absence gets a type: **szabadság** (leave), **beteg** (sick), **egyéb** (other). The
solver treats them all alike: absent is absent.

- **The month grid** gets a type picker above it (*Szabadság · Beteg · Egyéb*, one active). Clicking
  or dragging paints the active type. Clicking a day that already has that type clears it; a
  different type is replaced. The bars carry the type in colour **and** a letter (*Sz*, *B*, *E*),
  so the colours don't have to carry it alone: leave the theme green, sick orange, other grey.
- **Print and Excel** say *szabadság*, *beteg* or *távol* instead of the single *távol*.
- **Call-in suggestions prefer leave:** people on leave first, then other, then the sick, who are
  marked *(beteg)*. `explain`'s *"Hívj be valakit: …"* list follows the same order.

**Leave balance.** Each person may have a **yearly leave allowance** in days, set on the
Munkatársak tab (empty = not tracked, the default). The absence grid's name column is then headed
*"Szabadság 2026"* (the shown month's year) and shows *"32 / 50"* next to each tracked name: leave
days used in that calendar year out of the allowance plus any days carried over. **Carry-over** is
a number per person per year that she types in — clicking the balance opens that year's field under
the name; nothing is carried automatically.

- **Decision: the leave year is the calendar year, not the kindergarten year.** Hungarian leave
  is counted per calendar year (Mt. 122. §); the kindergarten year only matters for the roster
  balance (C).
- **Decision: carry-over is typed, not computed.** The rules for what may carry over (and until
  when) vary; she knows her numbers, and a wrong automatic figure is worse than an empty one.
- Going over the allowance is shown (the number turns orange) but not blocked.

**Schema 1 → 2.** `Absence` gains `type`; `Staff` gains optional `leaveAllowance` and
`leaveCarry: Record<year, days>`. The migration gives every v1 absence the type `leave`.
**Decision:** v1 was only used to plan break weeks, where an absence is almost always leave;
she can repaint the rare sick day.

## E. Month overview polish

Spec §13 says only *"Month overview polish."* **Decision — what it means here:** the Távollétek
month grid, the app's only month view, made easier to read at a glance:

1. **Today's column** is outlined.
2. **School-break days** get a tinted header, since those are the weeks she plans.
3. **A count row per role** under each section: how many teachers / nannies are away that day,
   orange when fewer are left than that week's group count needs for zero holes (`zeroHoleNeeds`:
   2 teachers a group, a nanny a group but at least 2) — an early hint before she opens the roster.
4. **The name column stays put** while the grid scrolls sideways.
5. **Ma** button next to ◀ ▶ jumps back to the current month.

## Testing, for all five

The same rules as v1 (spec §11): tests first, in `tests/` mirroring `src/`, behaviour over
styling, `validateRoster` guarding every roster. Additions:

- **B:** a property test — random swaps on random solved periods either return a roster that passes
  `validateRoster` or are refused; never a broken roster.
- **C:** a hand-built three-week history where the yearly stage must hand the extra unit to the
  person behind; the golden week stays unchanged (it has no history).
- **D:** a v1 backup restores into v2 with every absence typed `leave`.

## Privacy

Unchanged (spec §14). Leave allowances are her data like the rest: they stay in her browser and in
her backups.
